Bug Report · Frontend Auth State / Navigation Race

401 on /sessions/start and /auth/refresh Immediately After a Successful Password Reset

Date 3 August 2026 Reported by Martin Martinov (staging test) Severity High — player cannot enter the game after resetting their password Status Root cause confirmed · frontend fixed · backend hardening deferred
01

The Register Page Navigated Into the Game on a Leftover Access Token

“Played the game successfully, finished it. Then tested forgot password. Got the code from email, it verified successfully. After trying to login got 200, but afterwards got 401 on /sessions/start and 401 on /auth/refresh one after the other.”

Bug Confirmed

Root cause

RegisterPage.watchAuthAndNavigate() polled authStore.isAuthenticated() every 200 ms and navigated to /game the moment it read true. That signal is nothing more than !!accessToken() (core/stores/auth/auth.store.ts:35), and the access token lives in memory for the entire SPA lifetime — nothing signs the player out after a finished game (logout() was only ever reachable from the 401 handler in auth.interceptor.ts:56).

So on submit the condition was already satisfied by the token from the previous game. The poll fired at t≈200 ms and navigated before the login response came back — a staging login (network round trip plus a bcrypt verify) reliably takes longer than that. The game page then started a session using the old credential.

Normally that is invisible: in a plain “played, then logged in again” flow the old token is still valid, so the request succeeds and nobody notices. A password reset is what made the stale token detectably dead — AuthController::resetPassword revokes every token on the account (pm-trivia-BE/app/Http/Controllers/Api/AuthController.php:244-245).

The offending code (before the fix)

// trivia-app/src/app/pages/register/register.page.ts

async loginSubmit(): Promise<void> {
  ...
  this.authStore.login({ email: email!, password: password! });
  this.watchAuthAndNavigate();          // <-- starts polling immediately
}

private watchAuthAndNavigate(): void {
  ...
  this.authCheckInterval = setInterval(() => {
    if (this.authStore.isAuthenticated()) {     // <-- true from the OLD token
      ...
      this.router.navigate(['/game']);          // <-- races the login response
    }
  }, 200);
}

Why the same stale state also defeated the guard

authGuard (core/guards/auth.guard.ts:11) gates on the same isAuthenticated() signal, so it waved the navigation through for exactly the same reason. There was no second line of defence between the leftover token and /sessions/start.

02

Why Two 401s With Two Different Messages, One After the Other

The two failures are a single cascade, not two independent problems — and the second one destroyed the session that login had just created.

Sequence

Timeline

Step What happened Token state
1 Game played and finished. Nothing logs out. access A live
cookie R live
2 Navigated to the forgotten-password wizard. In-app routing, no page reload. A and R untouched
3 Reset succeeded. resetPassword deletes all Sanctum tokens and all PlayerRefreshToken rows (AuthController.php:244-245). Neither the store nor the browser cookie is cleared. access A dead
cookie R dead
4 Login submitted. Poll armed; at t≈200 ms it reads the stale A, passes authGuard, navigates to /game. store still holds A
5 GamePage.ngOnInit → startSession() (game.page.ts:95) sends Bearer A. 401 Unauthenticated.
6 Interceptor sees a 401 with a token present (auth.interceptor.ts:41) and attempts a refresh. The browser sends the stale cookie R; no matching hash exists. 401 Invalid or expired refresh token.
7 isAuthFailure → authStore.logout() → redirect to /register. the good tokens from step 4's 200 are wiped

Where each message comes from

  • Unauthenticated. — Laravel’s stock auth:sanctum rejection. The token row was deleted, so there is nothing to resolve.
  • Invalid or expired refresh token. — pm-trivia-BE/lang/en/api.php:16, returned by AuthController::refresh when the hash lookup misses. Note it is not No refresh token. (api.php:15) — proof the cookie was transmitted and simply no longer matched anything in the database.

Why the 200 on login appeared first in the network panel

DevTools orders rows by request start time, not by response time. The login request starts at t=0 and answers at roughly t≈400 ms; /sessions/start starts at t≈210 ms. Login therefore sits above the two 401s even though its response landed last — which is exactly why the fresh token arrived too late to be used, and was then cleared by step 7.

03

Frontend Fixes Applied

Two changes: stop trusting a leftover token, and stop navigating before the response that issued the current one.

Fixed

1 · Discard stale credentials before every auth attempt

register.page.ts:343-355 — new dropStaleSession(), awaited at the top of both submit() (line 311) and loginSubmit() (line 336). After this, isAuthenticated() — and therefore authGuard — can only become true from the response that just came back.

private async dropStaleSession(): Promise<void> {
  if (!this.authStore.isAuthenticated()) return;
  await this.authStore.logout();
}

Side benefit: a wrong-password 401 no longer arrives with a token attached, so the interceptor stops firing a doomed /auth/refresh (and its logout-plus-redirect) on ordinary failed logins.

2 · Gate navigation on the request status, not on isAuthenticated()

register.page.ts:357-390 — watchAuthAndNavigate() now waits out isPending() and enters the game only when the attempt is fulfilled. This is race-free by construction: requestStatus flips to 'pending' synchronously inside login()/register() before the poll is armed, and the store writes the new token immediately before flipping to 'fulfilled' (auth.store.ts:79-83) — so whenever the poll observes fulfilled, the token in hand is the one that request returned.

this.authCheckInterval = setInterval(() => {
  if (this.authStore.isPending()) return;               // still in flight

  clearInterval(this.authCheckInterval!);
  this.authCheckInterval = null;

  // rejected credentials / expired QR / throttled bucket:
  // the error toast covers it, the player stays on the form
  if (!this.authStore.isFulfilled() || !this.authStore.isAuthenticated()) return;

  const player = this.authStore.player();
  if (player) this.playerStore.setPlayer(player);
  this.router.navigate(['/game']);
}, 200);

3 · Log out locally when a password reset succeeds

forgotten-password.page.ts:195-217 — submitNewPassword() now awaits authStore.logout() before showing the done screen, mirroring the backend revoking every token on the account. Left in place, that state still read as a valid login to the guards, and the next authenticated call would go out with a credential the API had already thrown away.

AuthStore is the one store this page touches, and only to discard state — recorded in the class doc comment (:65-68) so it does not read as breaking the page’s deliberate “no stores” rule.

4 · Deliberately not changed: GameStore in the reset flow

register.page.ts’s ionViewWillEnter already converts a genuinely active session to abandoned and toasts the player. Resetting the game store from the forgotten-password page would swallow that notice for someone who resets their password mid-game, so the game store is left alone there.

04

Backend Findings — Deferred by Decision

The backend behaved correctly in this incident. These are hardening items, not the cause; left untouched on request.

Pending

A · A revoked refresh cookie is never cleared from the browser

resetPassword deletes the PlayerRefreshToken rows but sends no Set-Cookie, and refresh() likewise returns its two 401s (AuthController.php:128, 136) without expiring the cookie it just rejected. The dead cookie therefore keeps being sent for its full 30-day lifetime.

With the frontend fix in place this is no longer harmful in the reset flow — a successful login overwrites the cookie (same name, path and domain). What remains is noise: AuthStore’s cold-start silent refresh (auth.store.ts:128) will 401 on every app load until the player logs in again. Note that WebAuthStrategy.clear() is a no-op whose comment claims “server clears the cookie on logout” (web-auth.strategy.ts:27-29) — which nothing currently does.

Suggested helper alongside refreshCookie() (AuthController.php:306-317):

private function forgetRefreshCookie(): \Symfony\Component\HttpFoundation\Cookie
{
    return Cookie::make(
        name: self::COOKIE_NAME, value: '', minutes: -2628000,
        path: '/api', secure: true, httpOnly: true, sameSite: 'None',
    );
}

Attach it to the resetPassword response and to both 401 returns in refresh(). Do not use Cookie::forget() here — it emits without Secure / SameSite=None, which Chrome rejects in a cross-site context, so the cookie would not actually be deleted.

B · Null-player guard in refresh()

AuthController.php:139 reads $record->player and then calls $player->tokens() with no null check. A refresh token whose player row has been deleted turns what should be a 401 into a 500.

C · The refresh cookie is third-party on staging

refreshCookie() sets no domain, so the cookie is host-only on backend.pm.trivia.kipo.work while the app is served from another host — a cross-site cookie. Chrome still sends it (this test proves it: the response was “Invalid or expired”, not “No refresh token”), but Safari and Firefox block it outright. Web players on those browsers get silently logged out the moment the 60-minute access token expires, with no way to recover. Setting the cookie on the parent domain (.pm.trivia.kipo.work) would resolve it.

Ruled out during the investigation

  • Cookie encryption mismatch. The API middleware group appends only SubstituteBindings (bootstrap/app.php:29) — no EncryptCookies — so the refresh cookie is plaintext on the way out and read as plaintext on the way in. Symmetric; not a factor.
  • Sanctum token expiry. Access tokens are minted with a 60-minute expiry (ACCESS_TTL_MINUTES); the token rejected in step 5 was minutes old at most. It failed because its row had been deleted, not because it aged out.
  • The password reset itself. All three wizard steps behaved exactly to spec, and the subsequent login returned 200 with a valid token — the credential change worked.
05

Verification

What was proven, and what still needs a manual pass.

Evidence

Confirmed

  • Root cause traced end to end through source: the stale-token poll (register.page.ts), the revocation that killed the token (AuthController.php:244-245), and the interceptor cascade that produced the second 401 (auth.interceptor.ts:41-61).
  • The two distinct error strings were matched to their exact origins, and Invalid or expired refresh token. rather than No refresh token. establishes that the cookie was transmitted.
  • Frontend: npx tsc --noEmit -p tsconfig.app.json clean after the changes.
  • No API contract changed, so there is nothing to mirror in the backend or the mock-backend.

Still open

  • Not verified at runtime in a browser. The project ships no *.spec.ts covering these pages, so one manual pass is needed: finish a game → reset the password → log in, and confirm /sessions/start now carries the fresh token and returns 200.
  • Worth re-checking the plain path too (finish a game → log in again without resetting), since the same race existed there and was simply masked by the old token still being valid.
  • Backend items A, B and C above remain unimplemented by decision. C in particular is a pre-event risk for Safari and Firefox players, independent of this bug.
