Security audit

Nineteen findings across the registration flow, the game-session API and the admin panel. The two that matter most: re-registering with someone else's email overwrites their password and hands back a valid session for their account, and the answer-recording endpoints skip the session-ownership check every other route already has, so any registered player can write into — and prematurely finalize — any other player's live game.

2 Critical Account or environment compromise
4 High Cross-player impact or credential exposure
7 Medium Real exposure, bounded blast radius
6 Low / hardening Worth fixing, nothing urgent forces it

Severity is exploit impact, not effort. Both criticals are single-endpoint fixes; the hardening backlog is mostly configuration.

Critical 2 findings

Either of these compromises an account or the whole staging environment, with no special access required beyond a scanned booth QR token.

SEC-01

Account takeover via re-registration

Auth · every registered email

What happens

  • pm-trivia-BE/app/Http/Controllers/Api/AuthController.php:54
$player = Player::updateOrCreate(['email' => $data['email']], [
  … 'password' => $data['password'] …
]);

POST /auth/register with an already-registered email overwrites that player's password, name, phone and company, then returns a valid session for them. There is no ownership proof — no email verification, no existing-password check. The phone guard above it only fires if the attacker reuses the victim's phone; supplying their own phone sails through.

Anyone at the booth with a scanned QR token can take over any account whose email they know, and simultaneously destroy that player's PII record.

What to change

If the email already exists, require the password to match — i.e. treat the request as a login — or reject with 409.

SEC-02

Debug mode on the staging deployment

Configuration · full environment exposure

What happens

  • pm-trivia-BE/.env

APP_ENV=local, APP_DEBUG=true, LOG_LEVEL=debug, with APP_URL=https://backend.pm.trivia.kipo.work. If that env is what the staging host actually runs, every unhandled error returns a Laravel debug page exposing stack traces, SQL, config and environment variables — including APP_KEY and the MySQL credentials that are also in this file.

What to change

Confirm what's deployed. If it matches, set APP_ENV=production / APP_DEBUG=false and rotate APP_KEY and the DB password — anything printed by a debug page while it was live should be treated as burned.

High 4 findings

Each of these lets one player affect another's account, session or score, or leaves a credential-bearing surface unprotected.

SEC-03

Missing session ownership check on answer writes

Authorization · cross-player

What happens

  • pm-trivia-BE/app/Http/Controllers/Api/AnswerController.php:22, 43, 68
  • SessionController.php:131 — the authorizeSession() guard other routes use
  • AppServiceProvider.php:71 — sessions bind on seq_id, a small sequential integer

SessionController guards every session route with authorizeSession(), but AnswerController::store, sponsorAnswer and sponsorTrack never call it, and AnswerRecorder doesn't check either. Because sessions bind on a small sequential integer, any registered player can POST answers into any other player's live session — and finalizeIfComplete() (AnswerController.php:105) will then finalize the victim's session early, locking in a partial score and breaking their game.

What to change

Add the same authorizeSession() check used elsewhere to all three AnswerController methods.

SEC-04

Score inflation — answers unbounded by session

Business logic · leaderboard integrity

What happens

  • pm-trivia-BE/app/Services/Game/AnswerRecorder.php:23

The only guard is "this question wasn't already answered in this session." There is no check that the question belongs to the session's snapshot, that the session is still started, or that its time window hasn't expired. A player can walk the question-id space and submit an answer to every question in the bank — including sponsor questions at the 3× bonus — long after their session finalized, and final_score, which drives the leaderboard and prize selection, keeps incrementing.

What to change

Validate questionId against the settings_snapshot's question-id lists and the session's status/time window before recording.

SEC-05

Admin login and password reset are unthrottled

Auth · brute force

What happens

  • pm-trivia-BE/routes/auth.php
  • bootstrap/app.php — no default throttle on the web group
  • AppServiceProvider.php:26–64 — the player API's own rate limits, for contrast

No throttle middleware on POST /admin/login or POST /admin/forgot-password. Unlimited password guessing against the admin panel, and unlimited reset-mail sending. The player API is carefully rate-limited — the admin panel just got missed.

What to change

Apply throttle:login or a dedicated admin limiter to both routes.

SEC-06

Stored XSS in static pages

Sanitization gap · access-token exposure

What happens

  • pm-trivia-BE/app/Http/Controllers/Admin/SettingsController.php:207
  • trivia-app/src/app/pages/static-page/static-page.page.ts:49

Backend "sanitizes" with strip_tags($content, '<p><br>…<a>'). strip_tags removes tags, not attributes — <a href="javascript:…"> and <p onclick="…"> both survive. The frontend then calls bypassSecurityTrustHtml(page.content) with no DOMPurify pass. The register page does this correctly via sanitizeAdminHtml; the static page was missed. Script running on the FE origin can read the in-memory access token and drive the API with the credentialed refresh cookie.

What to change

HTML Purifier (or a similar attribute-aware sanitizer) server-side; run sanitizeAdminHtml() client-side on static-page.page.ts, same as the register page.

Medium 7 findings

Real exposure with a more bounded blast radius, or findings that amplify the criticals/highs above rather than standing alone.

SEC-07

Game endpoints have no rate limit

Amplifies SEC-03 / SEC-04

pm-trivia-BE/routes/api.php:63–68 — questions/next, answers, sponsor-answer, sponsor-track, complete and result carry no throttle at all. This amplifies SEC-03 and SEC-04, and lets the whole question bank be scraped with answers, since every answer response returns correctIndex.

SEC-08

Authorization policies are stubs and never invoked

Admin panel · any role

pm-trivia-BE/app/Policies/*.php all return true, and no controller calls authorize(). Only the global routes are gated by role:admin; the per-event group in routes/web.php requires nothing beyond auth:admin. Any admin-guard user of any role can export the full player PII CSV, delete players, and edit sponsors and game settings for every event.

SEC-09

The registration QR gate is effectively public

Feeds SEC-01

pm-trivia-BE/app/Http/Controllers/Api/BoothDisplayController.php:98 returns the live registrationToken from an unauthenticated endpoint. Booth display is intentionally token-free, so anyone who has the (publicly displayed) booth URL can mint authPlayToken values without being at the booth. Combined with SEC-01, that is the remote path to account takeover.

SEC-10

Admin session cookie not marked Secure

Transport · admin session

SESSION_SECURE_COOKIE is unset, so config/session.php's 'secure' => env('SESSION_SECURE_COOKIE') resolves to null. CORS_ALLOWED_ORIGINS also lists an http:// origin.

SEC-11

CSV formula injection in admin exports

Export · Excel/Sheets execution

PlayerController.php:207, 238, 245; DashboardController.php:43; ReportController.php:53. Player-supplied first_name/ last_name/company go straight into fputcsv; a name starting with =, +, - or @ executes when the export is opened in Excel.

SEC-12

SVG upload allowed for sponsor logos

Stored XSS · media origin

StoreQuestionRequest.php:63 (mimes:svg,png); event logos use the image rule, which may also accept SVG. Media is served from the API origin at /storage/media, so an SVG opened directly is stored XSS on the origin that holds the refresh cookie.

SEC-13

Redux DevTools enabled in production builds

Frontend · state exposure

trivia-app/src/app/app.config.ts calls provideStoreDevtools unconditionally, exposing store state — including the access token — to any installed browser extension.

Low / hardening 6 findings

Worth fixing, but nothing here is under active exploit pressure the way the sections above are.

SEC-14

Resubscribe restores both consents regardless of original opt-in

Consent, not security

UnsubscribeController.php:34 — resubscribe() sets both email_opt_in and sms_opt_in to true regardless of what the player originally consented to.

SEC-15

Debug env var makes every answer correct if ever set live

Config guard

AnswerRecorder.php:40 — game.debug_all_correct makes every answer correct if the env var is ever set on a live host.

SEC-16

Fortify auto-discovered on the admin guard, unverified reachability

Needs confirmation

Fortify is installed and auto-discovered with Features::registration() and views => true on the admin guard, but there's no app-level Fortify provider or app/Actions — verify /register, /login and /user/* aren't reachable on the admin host.

SEC-17

No CSP or security headers on the frontend

Defense in depth

.htaccess only rewrites; index.html sets none. A CSP would have substantially blunted SEC-06 and SEC-12 even with the sanitizer gaps in place.

SEC-18

Player passwords require only 6 characters

Auth policy

AuthController.php:36 — the minimum-length rule on player passwords is 6.

SEC-19

Static pages return any page id with no published/status check

Content gating

StaticPageController returns any page id with no published/status check — draft or unpublished content is served the same as live content if its id is known.

Suggested order of work Sequenced

Ordered by exploit impact. The first two steps close every path to account or session takeover found in this pass.

  1. Close the account-takeover and cross-session write holes

    Make re-registration on an existing email require the current password or reject with 409, and add authorizeSession() to the three AnswerController methods that skip it. Together these are the only paths that let one player compromise another's account or game.

    SEC-01 · SEC-03 — do first

  2. Lock down the staging environment

    Confirm whether APP_DEBUG=true is live; if so, flip it, set APP_ENV=production, and rotate APP_KEY and the DB password — anything a debug page could have printed while exposed should be treated as burned.

    SEC-02 — immediate, ops

  3. Bound score writes and throttle the API

    Validate questionId against the session's snapshot and status/time window before recording an answer, then add throttling to the admin login/reset routes and the unthrottled game endpoints.

    SEC-04 · SEC-05 · SEC-07

  4. Sanitize HTML at the source

    Swap strip_tags for an attribute-aware sanitizer server-side, run sanitizeAdminHtml() on the static page like the register page already does, and stop accepting SVG for sponsor/event logo uploads.

    SEC-06 · SEC-12

  5. Wire up authorization and close the remaining medium findings

    Implement the policy classes and call authorize() from the admin controllers, mark the admin session cookie Secure and drop the http:// CORS origin, prefix formula-injection-sensitive CSV cells, and strip provideStoreDevtools from production builds.

    SEC-08 · SEC-10 · SEC-11 · SEC-13

  6. Hardening backlog

    Decide whether the booth QR gate needs to stop handing out live registration tokens unauthenticated, add a CSP to the frontend, raise the player password minimum, gate static pages on published status, fix the resubscribe consent bug, and confirm Fortify isn't reachable on the admin host.

    SEC-09 · SEC-14 – SEC-19 — as capacity allows

Scope and method Read this before quoting the result

What was done

A static read of the frontend (trivia-app/, this repo) and the backend (pm-trivia-BE) — auth flows, session/answer controllers, admin routes and policies, CSV export paths, upload validation rules, and the frontend's HTML-sanitization and state-management setup. Findings are anchored to file:line references throughout.

What was not done

No dynamic testing. Nothing here comes from running requests against a live deployment, fuzzing, or an authenticated pentest session. SEC-02's claim about the staging .env and SEC-16's Fortify reachability both need a live check against the actual deployed host before being treated as confirmed incidents rather than configuration risk. Dependency/CVE scanning of installed packages was also out of scope.

What's solid

Refresh tokens are rotated and stored hashed; the password-reset flow uses hash_equals and a two-step code→token exchange with per-email+IP limits; unsubscribe links are HMAC capability tokens with a per-player signing key; integration settings are encrypted:json; the refresh cookie is httpOnly/Secure with a correct deletion counterpart; session finalization is row-locked; no SQL injection or unescaped Blade output was found; landing-page copy goes through DOMPurify. The structure is sound — the findings above are concentrated in a handful of places where a check that exists elsewhere in the codebase wasn't applied consistently.
