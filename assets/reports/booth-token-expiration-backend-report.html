The Booth Registration Token: 24-Hour Expiry Is Consistent, Its Lifecycle Is Not

The 24-hour TTL on the booth registration token is internally coherent — config, TTL and rotation cadence all agree. Four defects sit around it: the token is never issued on the day an event goes live, it rotates at 00:00 UTC rather than event-local time, it has no grace overlap, and until now nothing enforced it server-side. The last of those is half-closed by a frontend change already shipped; the rest are backend-only.

Scope pm-trivia-BE (staging/live) Severity High — org tablets unusable on day one, and mid-show on US events FE status Shipped in 89522f1

What Is Already Correct

Listed first so none of it gets rebuilt. The 24-hour value itself is not the problem.

00

The TTL, the Cadence and the Admin Copy All Agree

No change needed to the 24-hour value or to the request-validation layer.

Verified

config/game.php:39 sets booth_rotate_hours => 24; RotateRegistrationTokens.php:29 turns that into a 1440-minute TTL; routes/console.php:35 schedules the command ->daily(). TTL matches cadence. The admin copy matches the intent too — “Scan this QR code every day on all of your organization's tablets… It refreshes automatically and stays active for 24 hours” (registration-qr.blade.php:17).

The auth endpoints already accept the token

Both register and login validate 'authPlayToken' => 'nullable|string|max:64' (AuthController.php:39 and :106) and call validateRegistrationToken() (:42, :109). Tokens are Str::random(32), comfortably inside max:64 and the string('token', 64) column.

bootstrap/app.php:44 renders JSON for api/*, so abort(410, $msg) emits {"message": "…"} — precisely the shape the frontend reads. The frontend change in 89522f1 therefore needs no backend work to function. It activates a path that was already built and simply had nothing feeding it.

01

No Booth Token Exists Until the First Midnight After the Event Goes Live

The most likely of these to be hit, because it lands on the morning of the show.

Bug

Root cause

Booth tokens are created in exactly one place — the scheduled command — and it only considers events that are already live:

// app/Console/Commands/RotateRegistrationTokens.php:31
Event::where('status', 'live')->get()->each(function (Event $event) use ($type, $ttlMinutes) {

Nothing issues a token when an admin flips an event from draft to live. There is no model observer and no call in the admin controller — the only other caller anywhere in the repo is DevSeeder.php:26.

Observed behaviour

An event set live at 08:00 on show day has activeRegistrationToken('booth') === null for the rest of that day. The admin panel then renders the placeholder instead of a QR:

{{-- resources/views/components/registration-qr.blade.php:58 --}}
QR not available yet — it becomes active once the event is live.

The message is actively misleading: the event is live. Staff have no way to enable any organization tablet until 00:00 UTC.

Note the per-player token is unaffected — it rotates every ten minutes (routes/console.php:28), so it appears within minutes of the event going live. This is specific to the booth token.

Caveat on severity

This only bites when the event is flipped live on show day. If it is created as live the day before, the midnight run picks it up and a token exists by morning. Whether this is currently a live outage therefore depends on operational practice — but the natural workflow is to go live on the day, so it should not be left to habit.

Suggested fix

Issue a booth token (and a player token) on the draft → live transition — an Event observer on updated() watching isDirty('status'), or an explicit call in the admin controller that performs the transition. Make it idempotent so re-saving a live event does not mint duplicates.

02

Rotation Fires at 00:00 UTC, Not at Event-Local Midnight

On a US show this puts the cutover inside booth hours.

Bug

Root cause

config/app.php:71 is 'timezone' => 'UTC', and the booth schedule carries no ->timezone() call:

// routes/console.php:35
Schedule::command('registration-token:rotate booth')
    ->daily()                    // ← 00:00 UTC
    ->withoutOverlapping(1)
    ->runInBackground();

Yet every event carries its own timezone column, honoured elsewhere in the codebase — BoothDisplayController::buildPayload() uses it for the daily leaderboard window, and registration-qr.blade.php:27 uses it to render the token's own “Active until” label.

Consequence

For an event in America/Chicago (UTC−5 in summer), 00:00 UTC is 19:00 the previous day, local — inside show hours. Every organization tablet's token expires at 7 pm and every tablet must be re-scanned on the spot, mid-event.

The booth token is precisely the one that must not flip during the day: the whole point of the 24-hour TTL is a once-daily, out-of-hours re-scan.

Suggested fix

Rotate per event at a local, pre-open hour rather than globally at UTC midnight — for example run the command hourly and have it issue for events whose local time has just passed 04:00, or schedule per-event with ->timezone($event->timezone). Either way the cutover should land well before doors open, not at an arbitrary UTC boundary.

03

No Grace Overlap, Unlike the Player Token

The player token was deliberately given an overlap; the booth token was not.

Hardening

The asymmetry

// app/Console/Commands/RotateRegistrationTokens.php:27-29
$ttlMinutes = $type === 'player'
    ? config('game.registration_token.player_rotate_minutes')
        + config('game.registration_token.player_grace_minutes')   // 10 + 1
    : config('game.registration_token.booth_rotate_hours') * 60;   // 24h, no grace

The player token intentionally outlives its rotation by a minute — config/game.php:34 explains it as “grace overlap so a phone scanned just before rotation still gets in.” The booth token gets an exact 24 hours against a 24-hour cadence, so there is zero overlap.

Two effects

  1. Hard cutover. The outgoing token is invalid the instant the new one is minted. A tablet that has not re-scanned is dead with no transition period.
  2. A brief window with no valid token at all. The command prunes before it creates (:32-36 then :37-42), and runs via runInBackground() off a schedule:run tick. Between the old token's expires_at and the insert, activeRegistrationToken('booth') returns null — so the admin panel shows the “not available yet” placeholder and no tablet can be enrolled. Seconds, not minutes, but avoidable.

Suggested fix

Add a booth_grace_hours setting mirroring the player pattern (TTL = 24h + grace), and stop pruning a token that is still inside its grace window. That makes the handover overlap rather than butt up, and closes the null window as a side effect.

04

A Missing authPlayToken Is Still Accepted

Half-closed by the frontend change; the remaining half is backend-side.

Hardening

Background — why this was invisible

Until commit 89522f1 the frontend never sent authPlayToken at all. It verified the QR through the separate GET /register/verify-token endpoint and then posted /auth/register without the token, so validateRegistrationToken() returned early every time.

Two things followed. The gate was purely client-side — and the 410 branch was unreachable, which means the per-event qr_rescan_message was never once shown to a player, despite being a required field in both admin forms whose hint promises it is “Shown when a player tries to register or log in with a QR code that has since rotated out.” Players always saw the frontend's own hardcoded copy instead. The frontend change fixes that: the message now reaches them verbatim.

What remains

The field is still optional, and the helper returns on null:

// app/Http/Controllers/Api/AuthController.php:252-256
private function validateRegistrationToken(?string $token): void
{
    if (! $token) {
        return;              // ← omit the field and the QR gate does not apply
    }

Honest clients are now gated. A request that simply omits authPlayToken still registers and plays with no QR at all.

Suggested fix — and one trap to avoid

Do not change the rule to required. That produces a 422 in Laravel's validation-error shape, so a player with a missing token would get a generic field-validation message instead of the event's re-scan copy — losing exactly the behaviour we just restored.

Keep nullable in the validation rules and abort inside validateRegistrationToken() when the token is null, so missing and expired both land on the same 410 with qr_rescan_message. If ungated registration must remain possible for any deployment, gate that on a config or per-event flag rather than on the field's absence.

05

The Token Is Not Scoped to Its Event or the Event's Status

Pre-existing and currently harmless; becomes a hole with two concurrent events.

Design decision

Observation

Both the verify endpoint and the auth-side helper look tokens up globally, checking only expiry:

// app/Http/Controllers/Api/RegistrationTokenController.php:22
RegistrationToken::where('token', $token)->where('expires_at', '>=', now())->exists();

// app/Http/Controllers/Api/AuthController.php:258
RegistrationToken::with('event')->where('token', $token)->first();

No event_id match and no check that the owning event is still live. This is a consequence of the design rather than an oversight — the auth routes sit outside the resolve.event middleware group, so there is no event context at register/login time. Not matching on type is correct and deliberate: one endpoint validates both kinds.

When it matters

With a single live event, never. With two concurrent events, a token issued for event A admits a player to event B. A token belonging to an event since paused or ended also keeps working until its own expiry — up to 24 hours for a booth token.

Worth an explicit decision now rather than a surprise the first time two events overlap. If the answer is that tokens should be event-scoped, the auth request needs to carry the event, or the token lookup needs to resolve it and reject non-live owners.

FE

The QR Token Now Travels on the Auth Call Itself

Type-checked clean. The FE project has no test suite, so that is the available verification.

Shipped

1 · core/models/api.models.ts

Added optional authPlayToken?: string to RegisterRequest (line 49) and LoginRequest (line 55), mirroring the backend's nullable|string|max:64.

2 · pages/register/register.page.ts

Both submit paths now send the token — line 328 in submit(), line 349 in loginSubmit():

this.authStore.register({
  …
  authPlayToken: this.activeToken ?? undefined,
});

No store change was needed: AuthStore.register/login pass the request object straight through to ApiService.

The pre-flight verifyTokenIsStillValid() call was kept, deliberately. It still does two things the server cannot: it catches the “no token at all” case (which the nullable field accepts), and it sets the tokenBlocked signal that disables both submit buttons and renders the in-card notice. The store's error path only raises a toast, so without it a rejected player could keep resubmitting into the same 410.

3 · pages/register/register.page.ts — unrelated fix in the same commit

tryBoothToken() previously called boothTokenStore.clear() on any failure, including the catch branch. An offline blip, a 429 from the shared per-IP throttle, or a 5xx therefore wiped the tablet's stored booth token permanently and forced a re-scan over a transient error. clear() now runs only on an explicit valid: false (line 223).

Relevant to the backend because it interacts with defect 03: during the rotation window where no valid booth token exists, the old behaviour would have had every polling tablet discard its token.

4 · core/interceptors/mock.interceptor.ts

Added a rejectExpiredQr helper (line 289) that answers 410 with a re-scan message when authPlayToken === 'expired', reusing the sentinel the existing verify-token mock already uses, plus a /auth/login route (line 312) which did not previously exist.

No error-handling wiring was required

apiErrorMessage() passes backend messages through verbatim (core/http/api-error.ts:71), AuthStore stores that via setError, and an effect in the register page toasts it. So qr_rescan_message now reaches the player automatically — that path was already built and only lacked something feeding it.

410 is deliberately outside isAuthFailure(), which matches 401/403 only, so an expired QR will not trigger a spurious logout in the auth interceptor.

Asks, in Priority Order

  1. Issue a booth token on the draft → live transition (defect 01). Without this, organization tablets cannot be enabled on the day an event goes live — the highest-impact item.
  2. Move booth rotation off 00:00 UTC to a pre-open, event-local hour (defect 02). Currently every tablet at a US-Central event loses its token at 7 pm local, mid-show.
  3. Add a grace overlap for the booth token (defect 03), mirroring player_grace_minutes, and stop pruning tokens still inside grace.
  4. Abort on a null authPlayToken instead of returning early (defect 04) — keeping the rule nullable so the rejection stays a 410 carrying qr_rescan_message, not a 422.
  5. Decide whether registration tokens should be event-scoped (defect 05) before two events ever run concurrently.

Items 1–3 are independent of the frontend commit and can land in any order. Item 4 is the only one that interacts with it, and the frontend already sends what it needs.
