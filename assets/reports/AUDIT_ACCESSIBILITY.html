Accessibility audit

Twenty-three findings across the player app, booth display and shared theme layer. The headline result: the game itself cannot be played without a pointing device — every answer choice is a <div> with a click handler. Alongside that, the registration form's labels are not attached to their inputs, pinch-zoom is disabled document-wide, and the brand orange fails contrast at every size it is currently used as text. All four are small, contained fixes.

4 Blocker Excludes a whole group of users outright
7 Serious Clear AA failure; usable but degraded
8 Moderate Conformance gap, low user friction
4 Advisory Best practice or accepted risk to record

Severity is user impact, not effort. Most blockers here are one-line or one-element changes.

Blockers 4 findings

Each of these makes some part of the product unusable rather than awkward. They are the set worth fixing before the app is presented as accessible to anyone.

A11Y-01

Answer choices are clickable <div>s, so the game is keyboard-inaccessible

2.1.1 · 4.1.2 (A)

What happens

  • game.page.html:100–111
  • sponsor.page.html:237–248

The answer cards are <div class="pm-answer" (click)="…">. A div is not focusable, exposes no role, has no accessible name, and does not fire on Enter or Space. There is no tabindex or keydown handler anywhere in the codebase to compensate.

The consequence is total: a keyboard-only player, a switch user, or a screen-reader user can reach the game screen, hear the question read out, and then have no way to answer it before the 90-second timer expires. The same pattern repeats in the sponsor bonus round.

What to change

Swap the element for a real button. .pm-answer already styles by class, so the visual result is unchanged once you reset the button defaults. 

- <div class="pm-answer" (click)="selectAnswer(choice.index)">
+ <button type="button" class="pm-answer"
+         [disabled]="selectedIndex() !== null"
+         [attr.aria-pressed]="selectedIndex() === choice.index"
+         (click)="selectAnswer(choice.index)">

Add width:100%; text-align:left; font:inherit; to .pm-answer, and replace the .is-disabled { pointer-events:none } lock-out with the native :disabled state. The sponsor round's pointer-events-none gate should become [disabled]="!unlocked()" on the same buttons.

A11Y-02

Registration and login labels are not associated with their inputs

1.3.1 · 3.3.2 · 4.1.2 (A)

What happens

  • register.page.html:83–154 — first name, last name, email, company, phone, password
  • register.page.html:245–272 — login email, password

Every field follows the shape <label class="pm-label">…</label> followed by a sibling <div class="pm-input-wrap"> containing the input. The label neither wraps the input nor carries a for attribute, so there is no programmatic association.

A screen reader announces each of the eight fields as an unnamed "edit text, blank". Registration — the only door into the product — is effectively unfillable, and tapping the visible label does not focus the field either.

What to change

The correct pattern already exists in this codebase: forgotten-password.page.html:48 and :53 use matched for/id. Apply the same to all eight fields. 

- <label class="pm-label">First name …</label>
+ <label class="pm-label" for="reg-first-name">First name …</label>
  <div class="pm-input-wrap">
-   <input class="pm-input" formControlName="firstName" />
+   <input id="reg-first-name" class="pm-input" required
+          formControlName="firstName" />

While in there: the required marker is a bare orange * conveyed by colour and symbol only. Add the native required attribute so it is exposed to assistive tech, and mark the decorative asterisk aria-hidden="true".

A11Y-03

Pinch-zoom is disabled for the entire application

1.4.4 · 1.4.10 (AA)

What happens

  • index.html:11
<meta name="viewport" content="viewport-fit=cover, width=device-width,
      initial-scale=1.0, minimum-scale=1.0, maximum-scale=1.0,
      user-scalable=no" />

This is a booth app played on personal phones by an audience that skews older, in variable trade-show lighting, on a screen carrying 11px body text (the SMS consent block). Locking zoom removes the one adaptation those users would reach for first.

iOS Safari has ignored user-scalable=no since iOS 10, so this mainly penalises Android and desktop Chrome users — inconsistently, which is worse.

What to change

Delete the three scale locks. Keep viewport-fit=cover.

<meta name="viewport" content="viewport-fit=cover,
      width=device-width, initial-scale=1.0" />

The layout is already fluid down to the 360px minimum from CLAUDE.md, so nothing else should need to move. Re-check the register card and the game HUD at 200% zoom after the change.

A11Y-04

Registration and login report no validation errors at all

3.3.1 (A) · 3.3.3 (AA)

What happens

  • register.page.html:196 — [disabled]="form.invalid || …"
  • register.page.html:283 — same on the login form

Neither form renders a single field-level message. The only signal that something is wrong is that the submit button stays greyed out at 45% opacity, with no explanation of which field or why.

A sighted user mistypes an email and sees a dead button. A screen-reader user hears "Start playing, dimmed" and has no route at all to discovering the cause. The "disabled until valid" pattern hides the error rather than reporting it — which is precisely what 3.3.1 exists to prevent.

What to change

Keep the button enabled, validate on submit, and render messages tied to their fields. forgotten-password.page.html:193–197 already does this for the password-mismatch case and is the pattern to copy. 

<input id="reg-email" …
       [attr.aria-invalid]="showError('email')"
       [attr.aria-describedby]="showError('email')
                                ? 'reg-email-err' : null" />
@if (showError('email')) {
  <p id="reg-email-err" class="pm-field-error">
    {{ 'REGISTER.EMAIL_INVALID' | translate }}
  </p>
}

Also add a form-level summary in a role="alert" container listing the invalid fields, and move focus to the first one on failed submit.

Serious 7 findings

Clear Level AA failures. The product still functions, but low-vision, colour-blind and screen-reader users get a materially worse version of it.

A11Y-05

The brand orange fails contrast everywhere it is used as text

1.4.3 (AA)

What happens

  • variables.scss:27 / tailwind.css:9 — --color-orange: #F34D23
  • _global.scss:219–248 — .pm-cta, white on orange

#F34D23 gives 3.56:1 against white — below the 4.5:1 floor for anything under 24px (or 18.7px bold). It is the colour of the primary CTA label, every inline link, the required-field asterisks, the token-expired banner text and the live score.

The CTA is the sharpest case: 16px at weight 800 (17px on desktop) is not "large text" under WCAG, so the app's single most important control fails.

What to change

The remedy is already in the token file. --color-orange-shade: #C7421B measures 4.97:1 on white — a barely perceptible shift that clears AA.

Use orange-shade for orange-on-white text, for white-on-orange button fills, and for the error banner. Keep #F34D23 for display type at 24px+, for glows, dots, bars and other non-text fills, where no minimum applies. On navy the orange is fine at 5.12:1 and needs no change.

A11Y-06

The correct-answer green fails contrast in its own success state

1.4.3 (AA)

What happens

  • variables.scss:37 — --color-correct: #16A34A
  • _global.scss:300–306 — .pm-answer.is-correct on #F0FDF4

#16A34A is 3.30:1 on white and drops to 3.15:1 on the mint background the correct answer is painted with — so the reveal moment, the one frame the player is actually looking at, is the least readable state in the app.

What to change

Darken the token to #15803D, which measures 5.02:1 on white and comfortably clears the mint tint too. The hue is unchanged; only the luminance moves.

The same applies to the easy difficulty dot in game.page.ts:256, which reuses this green.

A11Y-07

Muted text at reduced opacity — including the SMS consent copy — fails badly

1.4.3 (AA)

What happens

  • register.page.html:187–191 — text-muted/70 at 11px
  • register.page.html:301 — consent footnote, same treatment
  • leaderboard.page.html:77 — rgba(107,114,128,0.5)
  • tailwind.css:27 — --color-muted-light: #9CA3AF

The base --color-muted #6B7280 passes at 4.83:1. Every reduced-opacity derivative of it does not: muted/70 lands at 2.74:1, muted-light at 2.54:1, and the leaderboard's separator at 1.93:1.

The most consequential instance is the SMS frequency / rates / HELP-and-STOP block — 11px at 2.74:1. That is the exact disclosure a carrier reviewer expects to be legible at the point of collection, so this one carries compliance weight as well as accessibility weight.

What to change

Drop the opacity modifiers and use solid --color-muted for all of this copy. Raise the SMS disclosure from 11px to at least 12px while you are there — nothing in the layout depends on it staying at 11.

Retire --color-muted-light for text use, or redefine it to a value that passes; today it is a token that cannot legally carry body copy.

A11Y-08

Answer feedback is colour-only, and nothing in the app is ever announced

1.4.1 (A) · 4.1.3 (AA)

What happens

  • game.page.html:100–111 — right/wrong via border + background colour
  • game.page.html:109 — a bare ✓ text node
  • game.page.html:49–56 — timer and score, no live region

Correct and wrong are distinguished by a green or red border and tint. The only non-colour cue is a ✓ glyph on the correct row, which most screen readers voice as "check mark" with no context.

More broadly: the codebase contains three ARIA roles in total — two alerts and one status, all in auth screens. Nothing in the game announces anything. Score changes, streak multipliers, the ten-second timer warning and the round result are all silent.

What to change

Add a visually hidden live region on the game page and write the result into it when lastResult() resolves: 

<p class="sr-only" aria-live="assertive" role="status">
  {{ resultAnnouncement() }}
</p>
// "Correct. 240 points. Score 1,180."
// "Not quite — the answer was C, Tungsten carbide."

Mark the ✓ aria-hidden="true" once the text carries the meaning, and give the correct/wrong states a shape difference (icon or weight) as well as a colour difference.

The timer needs aria-live="off" plus a single polite announcement at the 30s and 10s marks — announcing every tick would be unusable.

A11Y-09

Focus indicators are removed on inputs and absent on most controls

2.4.7 (AA)

What happens

  • _global.scss:64–67 — .pm-input:focus { outline: none }
  • _global.scss:219, 251 — .pm-cta, .pm-cta-outline: no focus rule
  • sponsor.page.html:290 — focus:outline-none on the QR link, no replacement
  • leaderboard.page.html:18–27 — scope toggles, no focus rule

Inputs trade the browser's focus ring for a 1.5px orange border at 3.56:1 — a change that is easy to miss and fails the adjacent-contrast expectation. The primary CTA, the outline CTA, the leaderboard toggles and the header logo have no focus styling of any kind. The sponsor QR link explicitly removes its ring and puts nothing back.

What to change

The right pattern is again already present — .pm-input-affix (:133) and .pm-checkbox (:190) both do it correctly. Promote it to a shared rule: 

%pm-focus, .pm-cta, .pm-cta-outline, .pm-answer,
.pm-input, .pm-bar-logo-link {
  &:focus-visible {
    outline: 2px solid var(--color-orange-shade);
    outline-offset: 2px;
    border-radius: 8px;
  }
}

Delete the focus:outline-none on the sponsor QR anchor outright.

A11Y-10

The sponsor video has no captions and no accessible controls

1.2.2 (A) · 2.1.1 (A) · 4.1.2 (A)

What happens

  • sponsor.page.html:136–147 — <video>, no controls, no <track>
  • sponsor.page.html:136 — play surface is <div (click)="startVideo()">
  • sponsor.page.html:191 — play affordance is <div>▶</div>
  • sponsor.page.html:149–185 — mute button contains only an unlabelled SVG

The video is sponsor-supplied, carries audio, and gates the bonus question — answers stay locked until it finishes. A Deaf or hard-of-hearing player gets no access to its content; a keyboard user cannot start it at all, because both the wrapper and the play button are non-focusable divs. The mute toggle is a real button but announces as just "button".

What to change

Add controls to the video element and make the play overlay a <button> with a translated aria-label. Give the mute toggle an aria-label that reflects state, and aria-hidden="true" on its SVG.

Captions need a content decision, not just a code change: the admin panel currently accepts a videoUrl only. Add an optional captions VTT URL beside it and render <track kind="captions" default> when present. Failing that, a sponsor-supplied transcript rendered under the player satisfies 1.2.2 for prerecorded content.

A11Y-11

Loading states are invisible to assistive technology

4.1.3 (AA)

What happens

  • game.page.html:6–15, 29–37
  • sponsor.page.html:41–51
  • results.page.html:6–15 · leaderboard.page.html:31–42

The three-dot loader and its caption sit in plain <div>s. When a screen-reader user navigates to the game, the page goes quiet — with no indication of whether it is loading, broken, or finished — and then content silently replaces it.

What to change

Wrap each loader in role="status" aria-live="polite", mark the animated dots aria-hidden="true", and keep the existing caption text as the thing that gets announced. The countdown before the game starts (game.page.html:18–27) wants the same treatment.

A11Y-12

Every route shares one page title

2.4.2 (A)

What happens

  • index.html:6 — static <title>
  • app.routes.ts — no route declares title

All twelve routes report "Practical Machinist Trivia". Browser history, tab switching and the screen-reader page-change announcement all carry no information about where the user is.

What to change

Add title to each route definition. Angular's Router sets it automatically, and a TitleStrategy can append the app name.

A11Y-13

No landmarks and no way to skip the header

1.3.1 (A) · 2.4.1 (A)

What happens

There is no <main> element anywhere in the application. Page content sits in unlabelled <div>s inside ion-content, and <header> is repeated per page rather than living in a shell.

Screen-reader users lose landmark navigation entirely and must tab through the header on every route.

What to change

Wrap each page's content region in <main id="main"> and add a skip link as the first focusable element in app.component.html. A .sr-only utility that becomes visible on focus is the standard shape, and the app currently has no such utility — worth adding to _global.scss since findings 08 and 11 need it too.

A11Y-14

The header logo is a clickable image, and the sponsor logo is unlabelled

2.1.1 (A) · 2.4.4 (A) · 1.1.1 (A)

What happens

  • pm-header.component.html:3–7 — routerLink on an <img>
  • pm-header.component.html:13, 17 — alt="Event"

Putting routerLink on an image produces a click target that is not focusable and is not exposed as a link. Its alt describes the picture ("Practical Machinist") rather than the destination.

The sponsor logo beside it is labelled alt="Event" on both branches — uninformative, and it discards the sponsor name the backend already supplies.

What to change

<a routerLink="/register" [queryParams]="registerQueryParams()"
   aria-label="Practical Machinist Trivia — home">
  <img class="pm-bar-logo" src="assets/pm-logo.png" alt="" />
</a>

For the event logo, bind the sponsor or event name into alt. If it is purely decorative next to adjacent text, use alt="" deliberately — but "Event" is neither.

A11Y-15

Heading structure is invalid on register and missing on two other pages

1.3.1 (A)

What happens

  • register.page.html:31–42 — a <div> and <p> nested inside <h1>, styled text-transparent
  • sponsor.page.html:229 — question phase starts at h2, no h1
  • results.page.html — no heading element at all

The register fallback headline is both invalid markup (block content inside a heading) and invisible — text-transparent hides it from sighted users while screen readers still read it as the page's h1. The sponsor question and the results page have no top-level heading to orient by.

What to change

Flatten the register fallback to inline content inside the h1, and give it a real colour or remove it. Promote the sponsor question prompt to h1 for that phase, and add an h1 to results — the "Final score" block is the natural candidate.

A11Y-16

Admin-supplied sponsor colours ship with no contrast constraint

1.4.3 (AA)

What happens

  • sponsor.page.html:107 — [style.background-color]="sq.sponsor.primaryColor"
  • sponsor.page.html:119–122 — [style.color]="sq.sponsor.textColor"
  • booth-display.page.html:82 — same binding on the sponsor stripe

Brand colour and text colour come straight from the admin panel and are applied unmodified. Whatever an admin picks ships to every player — including combinations like pale yellow text on white, which no amount of frontend care can rescue.

This is the one finding that cannot be fully closed in the frontend, and it recurs every time a new sponsor is onboarded.

What to change

Put the check where the value is entered: in the admin colour pickers, compute the ratio between textColor and primaryColor live and block or warn below 4.5:1.

As a frontend backstop, derive the text colour from the chosen background (pick black or white by luminance) rather than trusting the stored pair, so a bad admin entry degrades to legible instead of invisible.

A11Y-17

Links inside admin rich-text content fail contrast

1.4.3 (AA)

What happens

  • tailwind.css:58 — .editor a { @apply text-blue-500 underline }

Tailwind's blue-500 (#3B82F6) is 3.68:1 on white. The .editor class carries the terms and privacy pages (/page/:id) and the admin-authored landing copy — the consent link a player is asked to read before agreeing.

What to change

Use blue-700 (#1D4ED8, 7.0:1) or the brand orange-shade for consistency with the rest of the app. The underline is already there, so colour is not the only link cue — but it still has to be readable.

A11Y-18

Decorative glyphs and initials are read aloud verbatim

1.1.1 (A)

What happens

  • results.page.html:55, 65, 72 — 🏆 📅 in content divs
  • sponsor.page.html:13, 191, 253 — ★ ▶ 🔒
  • leaderboard.page.html:61, 77 — initials avatar, · · · separator
  • game.page.html:109 — ✓

Every one of these is announced. "Trophy, view leaderboard" and "black star, bonus round" are merely noisy; the leaderboard's initials badge is worse, spelling out letters immediately before the full name is read, and the · · · rank-gap separator reads as "middle dot middle dot middle dot".

What to change

Add aria-hidden="true" to each. The initials badge is purely a visual restatement of the adjacent name, so it hides cleanly. Where a glyph carries meaning no text repeats — the 🔒 lock hint — keep the sentence and hide only the emoji.

A11Y-19

The leaderboard scope toggle exposes no selected state

1.4.1 (A) · 4.1.2 (A)

What happens

  • leaderboard.page.html:18–27

"Today" and "This week" are two buttons whose selection is communicated purely by a white pill background. Nothing in the accessibility tree distinguishes the active one, and the same is true for the current player's row, which is marked only by orange text.

What to change

Add [attr.aria-pressed]="store.activeScope() === 'today'" to each button — the app already uses aria-pressed correctly on the password toggles, so the pattern is established. For the current player's row, add a visually hidden "you" marker rather than relying on the orange.

Best practice, or judgement calls worth recording as accepted risk rather than silently leaving open.

A11Y-20

No prefers-reduced-motion support anywhere

2.3.3 (AAA)

What happens

animate-rise, animate-pop, dot-bounce, the countdown digit and the 60fps timer bar all run unconditionally. prefers-reduced-motion appears nowhere in the codebase.

None of it is large-area parallax, so the vestibular risk is modest — but the pop and bounce animations fire on every question transition, which is a lot of motion across a 90-second session.

What to change

@media (prefers-reduced-motion: reduce) {
  .animate-rise, .animate-pop, .loading-dot,
  .countdown-digit { animation: none; }
}

Keep the timer bar — it conveys state, not decoration — but drop it to discrete steps.

A11Y-21

Invalid autocomplete token on the registration password

1.3.5 (AA)

What happens

  • register.page.html:145 — autocomplete="password"

password is not a valid autocomplete token, so browsers and password managers ignore it. Every other field on the form is correct, and the reset flow uses new-password properly.

What to change

Change to autocomplete="new-password".

A11Y-22

The 90-second session timer cannot be paused or extended

2.2.1 (A) — exception claimed

What happens

  • game.page.ts:20, 157–177 — fixed session countdown
  • sponsor.page.html:62–68 — a second timer, gated behind the video

2.2.1 exempts limits that are essential to a real-time or competitive activity, and a timed trivia game with a shared leaderboard is a reasonable fit. The sponsor round is less clear-cut: its answer timer only starts after a video the player cannot skip, so two timing constraints stack.

What to change

Nothing structural. Record the exception explicitly in the accessibility statement so it reads as a decision rather than an oversight, and consider a configurable session length in the admin panel — an accessible-session mode at 180 seconds costs little and answers the objection directly.

A11Y-23

Booth display type is sized entirely in vw

1.4.4 (AA) — low exposure

What happens

  • booth-display.page.scss — every font-size in vw (e.g. 4.55vw, 0.83vw)

Viewport-relative type does not respond to browser zoom or OS text-size settings. On a normal page this fails 1.4.4 outright.

What to change

Low priority in practice: the booth display is an unattended TV view at a fixed distance with no user agent to zoom, which is exactly the case vw exists for. Leave it, but keep the pattern quarantined to this one page — it should not spread into the player app.

Suggested order of work Sequenced

Ordered by impact per hour, and because some steps unlock others — the shared .sr-only utility from step 3 is a prerequisite for several later fixes.

  1. Make the game playable by keyboard

    Convert both answer grids to buttons and give every interactive element a :focus-visible ring. This is the single change that moves the product from "inaccessible" to "usable".

    A11Y-01 · A11Y-09 — ~half a day

  2. Fix the registration form

    Associate all eight labels, add required, correct the autocomplete token, and render validation errors with a form-level summary. Registration is the only entry point, so a defect here excludes users from everything downstream.

    A11Y-02 · A11Y-04 · A11Y-21 — ~half a day

  3. Re-tune the colour tokens and unlock zoom

    Point orange text at orange-shade, darken the correct-state green, drop the opacity modifiers on muted copy, fix the editor link colour, and delete the viewport scale locks. All token-level; no component rewrites.

    A11Y-03 · 05 · 06 · 07 · 17 — ~2 hours plus a visual pass

  4. Add the announcement layer

    Introduce .sr-only, wire live regions for answer results, loading states and the countdown, and hide the decorative glyphs. This is where a screen-reader session stops being silent.

    A11Y-08 · 11 · 18 · 13 — ~half a day

  5. Structure and semantics

    Route titles, <main> landmarks and a skip link, the header logo link, heading hierarchy, and the leaderboard toggle state.

    A11Y-12 · 13 · 14 · 15 · 19 — ~3 hours

  6. Sponsor media and admin-side constraints

    Video controls and labelled buttons are frontend work; captions and a contrast guard on the sponsor colour pickers need backend and admin-panel changes, so start that conversation early even though the fix lands last.

    A11Y-10 · A11Y-16 — frontend ~3 hours, plus admin/BE work

  7. Reduced motion and the accessibility statement

    Add the media query, then write down the timer exception (A11Y-22) and the booth display's vw sizing (A11Y-23) as recorded decisions rather than open gaps.

    A11Y-20 · 22 · 23 — ~1 hour

Scope and method Read this before quoting the result

What was examined

  • All 13 page templates and the shared header component
  • _global.scss, variables.scss, tailwind.css, index.html
  • Route configuration and the game / sponsor page controllers
  • Every design-token colour pair, computed against the WCAG relative-luminance formula

What was not

  • No runtime testing. No axe or Lighthouse pass, and no screen-reader session on a running build
  • No testing with NVDA, JAWS, VoiceOver or TalkBack — the behaviours described are inferred from markup
  • Ionic's own component internals (ion-content, ion-toast) were taken as given
  • The Laravel admin panel was inspected only where it feeds colours and media into the player app

How severity was assigned

  • Blocker — excludes a group of users from completing a core task
  • Serious — clear AA failure; the task is possible but materially degraded
  • Moderate — conformance gap with limited practical friction
  • Advisory — best practice, or a judgement call to record deliberately

Recommended next step

  • Run axe DevTools against a built app once items 1–3 land — it will catch anything static review missed
  • Do one keyboard-only pass through register → game → sponsor → results, and one with a screen reader
  • A static audit reliably finds absent semantics; it cannot confirm how a real screen reader narrates them
