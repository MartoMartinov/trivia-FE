FE / BE Report · PM Trivia · 6 August 2026

The Leaderboard Day Never Ended, and the Game Never Finished

Both observations in the client's 6 August report are reproducible defects, and they are independent of one another. The daily leaderboard window is being computed against the UTC calendar day rather than the event's local day, so a midnight CST rollover does nothing. Separately, a session is only ever finalized when the player taps “See my results” — until that tap, the game does not exist to the leaderboard, the admin panel, lifetime totals, or prize selection. The first is almost entirely backend; the second needs work on both sides.

Reported by Ines Gonzalez Di Martino (PM) Environment frontend.staging.trivia.kipo.work Severity Show-blocking FE status Shipped — see below

Update, same day. The three frontend-owned items below have shipped: a session now finalizes the moment the sponsor round ends rather than waiting on a button tap, and the leaderboard, booth display, and mock backend all render a live countdown to the reset instead of static “midnight” copy. The backend items — the event timezone data fix, centralizing the day-boundary logic across eight queries, and server-side finalization on the last answer — remain open, and are what's left before this is fully closed.

What Was Reported, and What Each Symptom Actually Is

Three symptoms, two root causes. Mapping them before diving in, because the second and third symptoms share a cause and the first does not — which is why fixing one will not silence the others.

Symptom as reportedRoot causeOwner
“Played at 11:55 pm and 12:03 am CST and the leaderboard still only shows the 11:55 pm game.” A — daily window computed on the UTC day BE
“Shows it played 14 days ago, but I just played using it.” B — session never finalized BE FE

The client's own diagnosis of cause B is correct. She identified the “See my results” gate herself and asked for the leaderboard to populate without it. That request is not a UX preference — it is the fix for a data-integrity defect. Any player who closes the tab, loses signal, or simply walks away from the booth is currently discarded entirely.

Cause A — The Daily Window Runs on UTC, Not Event-Local Time

The leaderboard query itself is written correctly. The defect is in the data it reads its timezone from, and in the seven other places that never ask for a timezone at all.

BE

Midnight CST Falls in the Middle of the UTC Day

Why 11:55 pm and 12:03 am landed in the same “today”.

Bug

The query is right

The public leaderboard derives its window from the event's timezone, exactly as it should:

// app/Http/Controllers/Api/LeaderboardController.php:98-105
$tz = $event->timezone ?? 'UTC';

return $scope === 'week'
    ? [now($tz)->startOfWeek()->utc(), now($tz)->endOfWeek()->utc()]
    : [now($tz)->startOfDay()->utc(),  now($tz)->endOfDay()->utc()];

The booth display (BoothDisplayController.php:34-35) and the admin live leaderboard (Livewire/Admin/Dashboard/LiveLeaderboard.php:22-23) use the same pattern. No change needed to any of these three.

The data behind it is not

Two defaults conspire. The events table defaults the column to UTC — $t->string('timezone')->default('UTC') (create_events_table.php:18) — and the application default is UTC as well (config/app.php:71). If the staging event was created without an explicit timezone, $event->timezone is 'UTC' and the ?? 'UTC' fallback never even gets a chance to matter.

With $tz = 'UTC', the arithmetic produces precisely the reported behaviour:

EventLocal (CDT)UTCInside the UTC “today” window?
First game5 Aug, 23:556 Aug, 04:55Yes — still counted
Second game6 Aug, 00:036 Aug, 05:03Yes
Window opened at5 Aug, 19:006 Aug, 00:00—
Window closes at6 Aug, 19:007 Aug, 00:00—

Both games sit in the same UTC day, so the 11:55 pm entry never dropped off. The client's expectation — that only the 12:03 score should remain — is the correct one. (Chicago is on CDT, UTC−5, in August; the report's “CST” is the colloquial usage. The offset does not change the outcome — under either offset both games land in the same UTC day.)

The worse consequence she has not seen yet

Under UTC, the daily leaderboard resets at 19:00 local time — during show hours. The board would wipe itself in front of the booth at peak traffic, and the “one play per day” limit would silently reopen at the same moment. This is the part that makes cause A show-blocking rather than cosmetic.

BE

Eight Other Queries Ignore the Event Timezone Entirely

Setting the event's timezone fixes the leaderboard. It does not fix these, because they never read it.

today() and now() resolve against config('app.timezone'), which is 'UTC'. CURDATE() resolves against the database session timezone — a third, separate source of truth. So the admin panel and the public API do not currently agree on what “today” means, and neither reliably agrees with the show floor.

The one that needs escalating

Winner notifications select on rank_today:

// app/Console/Commands/DispatchNotifications.php:196
->whereBetween('rank_today', [1, 3])

rank_today is written by SessionFinalizer using the UTC day (line 30 above), and recomputed at DispatchNotifications.php:158. If the day boundary is wrong, the ranking pool is wrong, and the wrong players can receive “you won” messages. Prizes are involved, so this should not ship unresolved.

Suggested fix

  1. Immediate, no code: set events.timezone = 'America/Chicago' on staging and live. This alone corrects the public leaderboard, the booth display, and the admin live leaderboard — and moves the reset back to local midnight.
  2. Then centralise: one helper on Event (for example dayRange() / weekRange(), wrapping the existing dateRange() logic) and route every site in the table above through it. Replace the raw CURDATE() comparisons in PlayerController with bounded whereBetween on UTC instants so they stay index-friendly.
  3. Backfill: once the boundary changes, existing rank_today values were computed under the old rule. Recompute for any day still in the reporting window.

One decision to confirm with the client

The window filters on started_at (LeaderboardController.php:58), so a game begun at 23:58 and finished at 00:02 counts toward the earlier day. That is defensible and self-consistent, but it is a rule the client should be told rather than left to discover — it is the same class of surprise as the one she just reported.

Also worth stating explicitly: the board keeps one row per player, chosen by leaderboard_score_mode — best_score by default, or latest_score (LeaderboardController.php:63-66). Her two games were on two different accounts, so this did not affect what she saw, but under best_score a player's second game of the day will not replace a higher first game.

Cause B — A Game Only Counts If the Player Taps a Button

The score is committed by a client-initiated call that a player is free to never make. Nothing on the server compensates. This is the cause behind both the “14 days ago” anomaly and the delayed leaderboard entry. The frontend has since shipped a partial mitigation, below — the backend fix is what actually closes it.

BE + FE

Confirmed on both sides of the wire.

Bug

When the session has a sponsor round, game.page.ts hands off to /sponsor and deliberately does not complete:

Backend — no compensating path

SessionFinalizer::finalize() has exactly two callers in the whole repository, both client-triggered:

// app/Http/Controllers/Api/SessionController.php

And app/Console/Commands/ holds only DispatchNotifications, PurgeAnonymizedPlayersCommand, and RotateRegistrationTokens: there is no sweeper for stale sessions. A session left in started stays there permanently.

Suggested fix — backend leads

Primary. Finalize server-side the moment the game is actually over, rather than when a client says so: when the last answer is recorded (in AnswerRecorder / AnswerController, once no questions and no sponsor questions remain), and when the play window expires. SessionFinalizer is already safe to call repeatedly — it early-returns on status === 'completed' (:13-15) and takes lockForUpdate() (:19-22) — so this composes with the existing endpoints without a double-count risk.

Safety net. A scheduled command to finalize sessions still in started past their play window, so genuinely abandoned games resolve to a real score instead of lingering forever. This also gives the admin Abandoned tab an honest meaning.

Shipped — frontend, defense in depth

The outro is now purely presentational — “See my results” only navigates, and its own completeSession() call stays as a harmless, idempotent repeat rather than the sole trigger. This closes the gap for a player who reaches the outro and then closes the tab, which was the client's exact scenario. It does not close the gap for a player who abandons mid-sponsor-question, before ever reaching the outro — that case still needs the backend fix above.

Listing it here as outstanding work was inaccurate; no change was needed.

Adjacent Finding — The Reset Time Was Hard-Coded Copy

Not a cause of anything she reported, but it is why cause A stayed invisible until a PM happened to play either side of midnight. Shipped the same day this was filed.

FE

The API Sent the Real Reset Time; the UI Showed a Fixed String

Now renders a live countdown instead — turns a whole class of timezone bug into something a tester can see.

Shipped

What was wrong

The backend already returned the true end of the window — 'resetsAt' => $to->toIso8601String() (LeaderboardController.php:94) — and the frontend stored it: resetsAt was in the API model, the store slice, and the updater. Nothing rendered it. Every surface printed static text instead:

// src/app/pages/booth-display/booth-display.page.html:24 (before)
<span class="lb-resets">RESETS AT MIDNIGHT</span>

// src/assets/i18n/en.json (before)
"FOOTER":  "Daily leaderboard resets at midnight · Winners notified by SMS and email"
"RESETS":  "resets at midnight"

So the UI asserted “resets at midnight” while the API was reporting a 19:00 reset, and the two were never compared.

What shipped

A new util, formatCountdown() (src/app/shared/utils/format-countdown.util.ts), turns the ISO instant into the coarsest two relevant units — a countdown rather than a clock time, so it needs no timezone conversion on either side:

// src/app/shared/utils/format-countdown.util.ts
export function formatCountdown(iso, now = Date.now()) {
  const diffMs = new Date(iso).getTime() - now;
  if (diffMs <= 0) return '';
  const totalMinutes = Math.floor(diffMs / 60_000);
  const days = Math.floor(totalMinutes / 1440);
  const hours = Math.floor((totalMinutes % 1440) / 60);
  const minutes = totalMinutes % 60;
  if (days > 0)    return hours > 0 ? `${days}d ${hours}h` : `${days}d`;
  if (hours > 0)   return minutes > 0 ? `${hours}h ${minutes}m` : `${hours}h`;
  if (minutes > 0) return `${minutes}m`;
  return '<1 min';
}

Wired into leaderboard.page.ts (hero subtext and footer, both now “resets in {{ time }}”) and booth-display.page.ts (“RESETS IN 3H 12M”), each falling back to the old generic copy only until the first response arrives. Because the label is relative to now rather than an absolute clock face, it reads correctly regardless of which timezone the backend ends up sending — it doesn't need to know or guess one.

mock.interceptor.ts's resetsAt stubs were also switched from a fixed +8h offset to a real end-of-day instant, so testing against the mock exercises the same countdown path a tester would see against staging.
