Bug Report · Backend / Question Selection

Buffer Runs Out of Easy Questions Mid-Game

Date 25 July 2026 Author Martin Martinov Status Root cause confirmed · fix pending decision
01

Easy Questions Disappear From the Buffer After ~15–20 Questions

"Timer set to 90 sec, answering rapidly (~1 sec/question) — around question 15–20 I only get medium and hard in the buffer. Admin shows 35 easy, 39 medium, 50 hard questions."

Bug Confirmed

Symptom

Network log of GET /questions/next: early buffers lead with an easy question (id 6, id 15). From roughly question 15–20 onward, every buffer leads with medium (id 21) or hard — easy never reappears for the rest of the session, even though the admin panel reports 35 easy questions in the bank.

Root cause — an event_id scoping mismatch

The admin panel counts questions globally. The game can only serve the subset whose event_id matches the live event. easy is simply the tier that hits the wall first.

Evidence

1. The game filters strictly by the live event's id — every selection query in SessionStarter (firstQuestion, bufferFor slot 0/1, selectStandardIds):

// app/Services/Game/SessionStarter.php:119, 148, 213
->where('event_id', $eventId)   // $eventId = Event::where('status','live')->first()->id

2. Admin-created questions get event_id = NULL — neither creation path sets it:

  • Single create — Admin/QuestionController.php:63-73 (no event_id key)
  • CSV import — Admin/QuestionCsvController.php:93-98 (no event_id key)
  • No global scope / boot hook backfills it. The model even documents the intent: "Questions are NOT event-scoped: event_id stays nullable" (Question.php:13).

3. The admin count is global, no event filter:

// app/Http/Controllers/Admin/QuestionController.php:43
'total' => Question::count(),   // counts every row, incl. event_id = NULL

4. Only seeded questions carry the event id — DemoSeeder creates the bank with event_id set, 15 questions per difficulty (DemoSeeder.php:26, 180-181).

Why Q15–20, and why easy specifically

Tier Admin shows (global) Game-visible (event-scoped)
easy 35 ~15 (seeded only)
medium 39 ~15 (seeded only)
hard 50 ~30 (15 hard + 15 hard_plus, hard_plus disabled → merged)

bufferFor always fills slot 0 with the easiest available question, so an easy question is pulled into every buffer and answered on nearly every turn. At ~1 sec/question, the ~15 real easy questions are exhausted (moved into answered_ids + in_flight_ids) in roughly 15–20 turns. Slot 0's fallback then steps up the chain (easy → medium → hard), so from that point the buffer contains only medium/hard. hard lasts longest because it also absorbs the seeded hard_plus rows.

Frontend — not the cause

The FE consumes whatever the buffer contains. Its pickFromBuffer fallback to buffer[0] when the requested tier is absent (game.updaters.ts:43) is a symptom, not the origin — once easy is exhausted on the BE, a post-wrong-answer "easy" request correctly returns whatever tier is available instead.

Confirm on staging

SELECT difficulty,
       COUNT(*) FILTER (WHERE event_id = '<live-event-id>') AS in_event,
       COUNT(*) AS global
FROM questions
WHERE type = 'standard' AND status = 'active' AND deleted_at IS NULL
GROUP BY difficulty;

Expected: in_event ≈ 15 for easy while global = 35.

Fix options

Approach Complexity Notes
Make the game event-agnostic — drop ->where('event_id', …) filters in SessionStarterRecommended Low Matches the model's stated "NOT event-scoped" design; smallest change; aligns game pool with admin's global count.
Assign event_id on admin create + CSV import Medium Correct if questions are genuinely meant to be per-event going forward; requires backfilling existing NULL rows.
Scope the admin count to the live event Low Minimum fix — stops the admin panel from overstating availability, but doesn't grow the usable pool.

Options 1 and 2 are contradictory design choices — decide whether questions are scoped per-event or form a single global bank, then align both the admin panel and the game to it. Recommend also logging when a difficulty tier is genuinely exhausted, so a silent fallback up the chain stays observable.
