Performance audit

Twenty findings across the bundle, the render path and the two timed screens. The headline result: the header logo is a 4944 × 1980 PNG rendered at 28 pixels tall, decoded on every page of the app. Behind it, the Inter webfont is very likely never loading at all because its @import lands 46 KB into the compiled stylesheet, and the game timer runs a 60 fps signal write through zone.js for the full 90-second round. Three contained fixes, each measured below.

4 Critical Measurable cost on every session, every device
6 Serious Dead weight shipped, or work that never stops
6 Moderate Real but bounded; worth a sprint slot
4 Advisory Record it; act when the constraint bites

Severity is measured user cost, not effort. The two largest wins here are an image export and a one-line stylesheet move.

PERF-01

The header logo is a 4944 × 1980 PNG displayed at 28 pixels tall

Asset · every page

What happens

  • src/assets/pm-logo.png — 4944×1980, 131 KB
  • pm-header.component.html:3 — src="assets/pm-logo.png"
  • _global.scss:19–25 — .pm-bar-logo { height: 28px }, 44px ≥1024px

The logo renders at roughly 70×28 CSS pixels. The file behind it is 9.8 megapixels — about a 176× linear over-provision, or 12,000× by area. <pm-header /> is on the register, game, sponsor, results and leaderboard pages, so this is the shared cost of every screen in the app.

The transfer cost (131 KB) is the smaller half. The real cost is decode: the browser must allocate and fill a 4944×1980×4-byte bitmap — roughly 39 MB of RAM — and downsample it, on the main thread, before first paint. On a mid-range Android phone at a trade-show booth that is a visible stall, and on a memory-constrained device it is a plausible cause of tab eviction.

The same defect repeats at smaller scale: public/tv-logo.png is 2757×660 (83 KB) for the booth display, and assets/icon/web-app-manifest-512x512.png is 130 KB for a 512×512 icon that should compress to well under 20 KB.

What to change

Export the logo at the size it is actually used, at 2× for retina, and serve WebP with a PNG fallback. A 140×56 WebP of this mark will land around 3–4 KB. 

- <img class="pm-bar-logo" src="assets/pm-logo.png" …>
+ <img class="pm-bar-logo" width="70" height="28"
+      src="assets/pm-logo.webp"
+      srcset="assets/pm-logo.webp 1x, assets/pm-logo@2x.webp 2x"
+      fetchpriority="high" decoding="async" …>

Better still for a wordmark: if the source artwork is vector, ship it as SVG and the resolution question disappears entirely. Add width/height regardless — see PERF-15 for the layout-shift half of this.

Then do the same pass over tv-logo.png (needed at ~180px on the booth TV) and re-encode the manifest icon. Total saving across the three: roughly 330 KB of transfer and essentially all of the decode cost.

PERF-02

The Inter @import is at byte 46,133 of the stylesheet, so browsers discard it

Render-blocking · CSS validity

What happens

  • theme/custom/base/_fonts.scss:1 — the @import url(…)
  • global.scss:13 — pulled in after @ionic/angular/css/core.css
  • www/styles-UBSWK2RB.css — the @import resolves to offset 46,133

CSS requires @import to precede every other rule in a stylesheet. Because _fonts.scss is imported at position 3 of global.scss — after Ionic's core CSS and after Tailwind's @layer theme { … } block — the compiled output has ~46 KB of rules ahead of it. The build flags this itself: 

▲ [WARNING] All "@import" rules must come first [invalid-@import]
    src/global.scss:298:0:
      298 │ @import url("https://fonts.googleapis.com/css2?family=Inter:wght@…
  This rule cannot come before an "@import" rule

A non-leading @import is dropped, not deferred. The practical consequence is that Inter is likely never fetched in production and every screen falls back to the platform sans-serif — which is fast, but is not the design, and means the typography has never actually been seen as specified.

Worth fixing even if a given browser is lenient: @import inside a stylesheet is the slowest possible way to load a font. It serialises three round trips — HTML → styles.css → Google's CSS → the woff2 files — with text blocked behind all of them.

What to change

Move it out of CSS entirely and into index.html, where the preload scanner can start the font fetch in parallel with the stylesheet rather than after it. Delete line 1 of _fonts.scss. 

+ <link rel="preconnect" href="https://fonts.googleapis.com">
+ <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
+ <link rel="stylesheet"
+       href="https://fonts.googleapis.com/css2?family=Inter:wght@400..900&display=swap">

Note the range syntax: wght@400..900 requests the variable font — one file of roughly 35 KB — instead of the current 400;500;600;700;800;900, which is six separate static faces totalling well over 100 KB. The templates use all six weights (font-black ×48, font-bold ×37, font-semibold ×9, font-extrabold ×8, font-medium ×2), so trimming the list is not an option — but the variable font covers all of them at a third of the weight.

For a booth app on venue wifi, self-hosting the woff2 in src/assets/fonts/ with a <link rel="preload"> removes the third-party origin from the critical path altogether. That is the version I would ship.

PERF-03

The timer bar drives a full-app change detection pass 60 times a second for 90 seconds

Render · game + sponsor rounds

What happens

  • game.page.ts:165–177 — rAF loop calling timerProgress.set()
  • game.page.html:72 — [style.width.%]="timeLeftPct()"
  • sponsor.page.ts:249–262 — the same pattern, per sponsor question

Two things compound here. First, the app runs on zone.js (provideZoneChangeDetection, app.config.ts:18), and zone.js patches requestAnimationFrame. Every frame therefore schedules a change detection tick. Over a 90-second round that is ~5,400 full application checks, each re-evaluating the whole game template — the two translate pipes, the score, the streak, the answered count, all four answer cards and their five class bindings.

Second, the property being animated is width. Width is a layout property: each of those 5,400 updates invalidates layout and repaint for the bar and its containing block, rather than staying on the compositor. The bar sits directly under a blur-3xl decoration (line 43), which makes the repaint region more expensive than the 6-pixel strip suggests.

The visible symptom is frame drops during play on mid-tier hardware — precisely when the player is trying to read four answer options against a countdown.

What to change

The bar is a linear drain over a known duration. It does not need JavaScript at all — hand it to the compositor and delete the rAF loop from both pages. 

.pm-timer-bar {
  transform-origin: left center;
  animation: pm-drain linear forwards;
}
@keyframes pm-drain { from { transform: scaleX(1) } to { transform: scaleX(0) } }
- <div class="h-full bg-orange" [style.width.%]="timeLeftPct()"></div>
+ <div class="h-full bg-orange pm-timer-bar"
+      [style.animation-duration.s]="totalSeconds()"></div>

transform is composited, so the animation runs off the main thread and survives a busy tick. The binding is written once when the round starts instead of 60 times a second, and the existing 500 ms setInterval continues to own the MM:SS label and expiry detection — which is all it was ever needed for.

If the bar must stay JS-driven for some reason not visible in the source, at minimum run the rAF loop outside Angular (NgZone.runOutsideAngular) and write to the element's style directly rather than through a signal.

PERF-04

polyfills.ts is not in the build, so __Zone_disable_customElements never applies

Dead configuration · Ionic

What happens

  • angular.json:16 — "polyfills": ["zone.js"]
  • src/polyfills.ts:45 — import './zone-flags'
  • src/zone-flags.ts:6 — __Zone_disable_customElements = true

The build's polyfills array names the zone.js package directly. src/polyfills.ts is referenced only by tsconfig.app.json and tsconfig.spec.json as a type-checking input — it is never bundled. Neither is zone-flags.ts.

So the flag someone deliberately set, with a comment explaining that it "prevents Angular change detection from running with certain Web Component callbacks", has no effect. Ionic is built entirely from custom elements, so every connectedCallback, disconnectedCallback and attributeChangedCallback across every ion-* element on the page is currently scheduling a change detection tick.

This is not a large file, but it is the kind of finding worth surfacing precisely because the intent is already in the repo and everyone assumes it is live.

What to change

Point the build at the file that carries the flags: 

- "polyfills": ["zone.js"],
+ "polyfills": ["src/polyfills.ts"],

polyfills.ts already imports ./zone-flags before zone.js, which is the required order — the flag must be on window before zone.js reads it.

The strategic version of this fix is to leave zone.js behind altogether. The app is already fully signal-based — every page is OnPush, state lives in @ngrx/signals stores, and no template uses *ngIf or *ngFor. Moving to provideZonelessChangeDetection() would delete the 34.6 KB / 12.4 KB gzip polyfills chunk outright and make PERF-03's per-frame storm structurally impossible. That is a change worth its own branch and a full regression pass over the Ionic overlays (toasts, the router outlet's cached pages), not a drive-by — but it is the right destination.

PERF-05

@ngrx/store and Redux DevTools ship to production but the app never uses them

Bundle · measured

What happens

  • app.config.ts:36 — provideStore()
  • app.config.ts:37 — provideStoreDevtools({ maxAge: 25, … })

All four stores in this app are @ngrx/signals signalStores. A repo-wide search for @ngrx/store returns exactly two hits: the two import lines in app.config.ts. There is no reducer, no action, no selector, no Store injection anywhere.

The classic Redux store is therefore instantiated at bootstrap, and the DevTools extension bridge is installed and listening, to observe a store that will never receive an action. I confirmed REDUX_DEVTOOLS_EXTENSION is present in the built main.js. logOnly: !isDevMode() restricts time-travel in prod but does not stop the instrumentation from loading.

What to change

Delete both providers and both imports. If Redux DevTools is wanted for signal stores, @ngrx/signals has withDevtools(), which is the supported route and can be applied per store. 

- import { provideStore } from '@ngrx/store';
- import { provideStoreDevtools } from '@ngrx/store-devtools';
  …
-   provideStore(),
-   provideStoreDevtools({ maxAge: 25, logOnly: !isDevMode() }),

Then drop @ngrx/store from dependencies and @ngrx/store-devtools from devDependencies so they cannot creep back in. Measured saving is given jointly with PERF-06 below.

PERF-07

Three setIntervals are stored in local consts and never cleared on navigation

Leak · timed screens

What happens

  • game.page.ts:129 — const tick, the 3-2-1 pre-game countdown
  • sponsor.page.ts:226 — const poll, the answer-result poll
  • sponsor.page.ts:317 — const tick, the placeholder reel countdown

The codebase is careful about this elsewhere — game.page.ts holds timerRef, rafId, pollRef and revealRef as fields and clears them in both ngOnDestroy and ionViewWillLeave, with a comment explaining exactly why the Ionic outlet makes the latter necessary. These three intervals were missed.

The game countdown is the one with teeth. A player who backs out during the 3-2-1 sequence leaves an interval alive that will call beginPlaying() on a page they are no longer on — starting the 90-second timer, the rAF loop from PERF-03, and eventually forcing a navigation to the sponsor round or results from underneath whatever screen they are actually looking at. This is the same class of bug the ionViewWillLeave comment was written to fix.

On a booth tablet cycling players all day, these accumulate.

What to change

Promote each to a field and clear it alongside its siblings. 

- const tick = setInterval(() => { … }, 1000);
+ this.countdownRef = setInterval(() => { … }, 1000);

  private clearTimer(): void {
    …
+   if (this.countdownRef) clearInterval(this.countdownRef);
+   this.countdownRef = null;
  }

The sponsor page also needs the ionViewWillLeave hook that the game page already has — it currently relies on ngOnDestroy alone, which the comment in game.page.ts:105–108 explains is not reliable under IonicRouteStrategy. Its setTimeout at line 231 is untracked for the same reason.

PERF-08

The booth display polls forever with no teardown — on the screen designed to run for days

Leak · booth display

What happens

  • booth-display.page.ts:51–53 — timer(0, 10_000).pipe(switchMap(…)).subscribe(…)

There is no takeUntilDestroyed(), no Subscription field, and no ngOnDestroy. In fact takeUntilDestroyed appears nowhere in the codebase. Most of the other bare .subscribe() calls are one-shot HTTP requests that complete on their own, so they are fine — this one is an infinite interval.

The component is also a @Component in an Ionic router outlet, so it is cached rather than destroyed on navigation. Every visit to /booth-display/:id starts another permanent 10-second polling loop against the API, and they stack.

This is the screen the spec describes as an unattended TV left running at the booth. A leak here is not theoretical.

What to change

  ngOnInit(): void {
    const eventId = this.route.snapshot.paramMap.get('id') ?? '';
    timer(0, POLL_MS).pipe(
      switchMap(() => this.api.getBoothDisplay(eventId)),
+     takeUntilDestroyed(this.destroyRef),
    ).subscribe((res) => this.data.set(res));
  }

Two further things worth doing on this screen specifically, given it runs for hours: pause polling when the tab is hidden (document.visibilityState), and add retry with a backoff — as written, a single failed request kills the switchMap chain and the board silently freezes on stale data until someone reloads the TV.

PERF-09

Signal changes are detected by setInterval polling instead of effects

Render · three pages

What happens

  • game.page.ts:220–246 — polls gameStore.lastResult() every 100 ms
  • sponsor.page.ts:226–239 — polls lastSponsorResult() every 100 ms
  • register.page.ts:436–450 — polls authStore.isPending() every 200 ms

All three watch a signal for a change by waking up on a timer and reading it. Under zone.js each wake-up is a change detection tick regardless of whether the value moved, so the game page runs ten extra full-tree checks per second for the entire duration of every answer round-trip.

It also adds latency the player feels: up to 100 ms of dead time between the answer response arriving and the correct/wrong highlight appearing, on top of the deliberate 1,100 ms reveal delay. The register page adds up to 200 ms before navigating into the game after login.

The correctness comments on watchAuthAndNavigate() are careful and the reasoning about request status is right — it is only the detection mechanism that is doing it the hard way.

What to change

effect() already does exactly this, synchronously, with no timer: 

- this.pollRef = setInterval(() => {
-   const result = this.gameStore.lastResult();
-   if (!result) return;
-   … clearInterval(this.pollRef); …
- }, 100);
+ const ref = effect(() => {
+   const result = this.gameStore.lastResult();
+   if (!result) return;
+   ref.destroy();
+   untracked(() => this.revealAndAdvance(result));
+ }, { injector: this.injector });

The reveal setTimeout stays as-is — that delay is intentional UX. Only the "has the answer landed yet" poll is replaced. The same shape applies to the sponsor page, and to register.page.ts watching isPending().

PERF-10

No caching or compression headers, despite content-hashed filenames

Delivery · Apache

What happens

  • .htaccess — SPA rewrite rules only, seven lines
  • angular.json — "outputHashing": "all" on prod, staging and demo

The build already names every asset by content hash (main-OGTL2PWG.js, styles-UBSWK2RB.css), which is the hard half of cache configuration and it is done. But the deployed .htaccess sets no Cache-Control at all, so returning players — and the booth tablets being reloaded between players all day — re-validate or re-download the full 638 KB each time, depending on whatever the host's defaults happen to be.

There is likewise no mod_deflate or mod_brotli configuration. Compression may be enabled at the server level, but nothing in the repo guarantees it, and the gap between 638 KB and 190 KB is the whole argument.

What to change

Hashed assets are immutable by construction and can be cached for a year; index.html must never be cached or the hashes never update. 

<IfModule mod_deflate.c>
  AddOutputFilterByType DEFLATE text/html text/css application/javascript
                                application/json image/svg+xml
</IfModule>

<IfModule mod_headers.c>
  <FilesMatch "\.(js|css|woff2|png|jpg|webp|svg)$">
    Header set Cache-Control "public, max-age=31536000, immutable"
  </FilesMatch>
  <FilesMatch "^index\.html$">
    Header set Cache-Control "no-cache, must-revalidate"
  </FilesMatch>
</IfModule>

Worth confirming with the backend team which server actually terminates these requests — if it is nginx or a CDN in front of Apache, the equivalent belongs there instead and the .htaccess is not the file to edit.

PERF-11

Question images and the sponsor video are known in advance but never prefetched

Network · game + sponsor

PERF-12

A universal selector sets font-family on every element in the document

Style recalc

What happens

  • theme/custom/base/_fonts.scss:3–5 — * { font-family: var(--ion-font-family) }

font-family is an inherited property. Setting it on * defeats that inheritance entirely: instead of one declaration cascading down, every element in the tree — including everything inside Ionic's shadow-piercing styles — carries its own declaration to be matched and resolved on each style recalculation.

On a page like the leaderboard, or the booth display with its list of players, that is a few hundred extra selector matches per recalc. It also makes it impossible to use a different family anywhere without !important, which is a maintenance cost as much as a performance one.

What to change

- * { font-family: var(--ion-font-family); }
+ :root { font-family: var(--ion-font-family); }
+ input, button, textarea, select { font: inherit; }

The second line is the reason the * was probably reached for — form controls do not inherit fonts by default. Naming them explicitly costs four selectors instead of one per element.

PERF-13

angularx-qrcode pulls in a CommonJS dependency, causing an optimization bailout

Bundle · two routes

What happens

The production build reports:

▲ [WARNING] Module 'qrcode' used by 'node_modules/angularx-qrcode/fesm2022/angularx-qrcode.mjs'
            is not ESM
  CommonJS or AMD dependencies can cause optimization bailouts.

QRCodeComponent is used on the booth display and the sponsor outro. Because the underlying qrcode package is CommonJS, esbuild cannot tree-shake it and includes the whole library — encoder, all error-correction levels, and the canvas and terminal renderers — in those two lazy chunks.

Both chunks are lazy-loaded, so this does not touch first paint. It is listed here because the booth display is the route that most needs to start fast on a TV browser after a power cycle.

What to change

The lowest-effort option is to accept it and silence the warning via allowedCommonJsDependencies in angular.json, so it stops masking future bailouts that do matter.

The better option, if either QR gets attention for another reason: both call sites render a static URL into a fixed-size square. A small ESM QR encoder, or generating the SVG server-side alongside registrationToken in the booth-display response, drops the dependency entirely. The backend already owns the token — returning a qrSvg with it would be a clean contract change.

PERF-14

backdrop-blur sits over a playing video, with a timeupdate handler behind it

Compositing · sponsor round

What happens

  • sponsor.page.html:150 — mute button, backdrop-blur-sm
  • sponsor.page.html:197 — countdown badge, backdrop-blur-sm
  • sponsor.page.ts:196–200 — onTimeUpdate() on (timeupdate)

backdrop-filter must re-sample whatever is painted beneath it. When that is a playing video, the blurred region is recomputed on every video frame — two such regions here, both overlaid on the reel.

Compounding it, timeupdate fires between 4 and 60 times a second depending on the browser, and each one writes secondsLeft, which under zone.js is another change detection tick. The handler only needs whole seconds.

This is the screen where the sponsor's brand is on display, so smooth playback has commercial weight beyond the usual.

Replace both backdrop blurs with a flat translucent fill — bg-black/60 already provides most of the legibility, and the blur is barely perceptible at 36 px. Then guard the handler so it only writes on a real change: 

  onTimeUpdate(): void {
    const video = this.videoRef()?.nativeElement;
    if (!video) return;
    const left = Math.max(0, Math.ceil(video.duration - video.currentTime));
+   if (left === this.secondsLeft()) return;
    this.secondsLeft.set(left);
  }
PERF-15

No image carries intrinsic dimensions, so every one can shift layout as it loads

Stop the poll in ionViewWillLeave and restart it in ionViewWillEnter, which is the pattern the register page already uses for its own lifecycle work. A document.visibilityState guard in the store would cover the backgrounded-tab case at the same time.

PERF-18

The translation guard blocks the first route on an HTTP round trip

First paint

What happens

  • translation.guard.ts:13–18 — awaits translate.use('en')
  • app.config.ts:32–35 — loader fetches /assets/i18n/en.json
  • app.component.ts:18–19 — calls setDefaultLang / use again

Every route is gated on translationGuard, and on the very first navigation it waits for en.json over the network before the register page can render. That is a serialised round trip inserted between bootstrap and first contentful paint. Subsequent routes short-circuit on currentLang, so the cost is paid once.

The file is 8 KB and the app ships a single language, so this is small — but it is on the critical path and it is avoidable.

What to change

Add <link rel="preload" as="fetch" href="/assets/i18n/en.json" crossorigin> to index.html so the fetch starts with the HTML rather than after the router boots. That is a one-line change with no risk.

While in there: AppComponent.ngOnInit calls translate.use('en') a second time, duplicating what the guard already did. Harmless, but it makes the loading order harder to reason about than it needs to be.

PERF-19

Large blur radii on decorative elements across six pages

Paint

What happens

  • register.page.html:9, 12 — blur-[60px] at 467×341, blur-[80px] at 620×520
  • game / leaderboard / results / sponsor — blur-3xl (64px) glows

Each is a single static filter: blur() on a large rounded div, painted once and then composited. The cost is a one-off at page entry rather than per frame, so it does not show up during play.

On the register page there are two overlapping, the larger at 620×520 with an 80 px radius — that is a meaningful first-paint cost on the entry screen of the app, on the lowest-powered device likely to run it.

What to change

Nothing urgent. If the register page's paint time proves slow when measured on a real mid-tier Android device, swap the blurred divs for a pre-baked radial-gradient background, which produces a near-identical result with no filter pass. Measure before changing — this is a "confirm, then act" item, not a defect.

PERF-20

No service worker, on an app whose defining constraint is trade-show wifi

Delivery strategy

What happens

There is a site.webmanifest and full icon set, but no @angular/pwa and no service worker. Every player at the booth downloads the full 638 KB over the same congested venue connection, and a booth tablet reloaded between players does so repeatedly.

PERF-10's cache headers address most of this more simply, which is why this is advisory rather than serious — a correct Cache-Control policy gets the repeat-visit case nearly all the way there.

What to change

Do PERF-10 first and measure. If repeat loads at the venue are still slow, ng add @angular/pwa with a freshness strategy for the API and performance for the app shell would make the tablets effectively instant-loading.

Note the interaction with the booth display: a cached shell must not cache the /booth-display/:id API response, or the TV will show a frozen leaderboard. Scope the data strategy carefully if this is taken up.

Scope and method Read this before quoting the result

What was done

A full static read of trivia-app/src — 89 source files across pages, stores, guards, interceptors and the theme layer — plus measurement against a real ng build --configuration production. Byte sizes and gzip figures are taken from build output, not estimated. Image dimensions are read from PNG headers. The bundle saving quoted in PERF-06 comes from applying the change, rebuilding, diffing, and reverting; the working tree is unchanged.

What was not done

No runtime profiling. Nothing here comes from Lighthouse, a Chrome performance trace, or a real device. Frame-rate and decode claims are reasoned from the code and the asset dimensions — they are well-founded, but they are predictions, not measurements. Before and after the work above, run a trace on the lowest-spec Android phone you expect at the booth, throttled to the venue's realistic bandwidth. Two numbers matter: time to first contentful paint on /register, and dropped frames during a 90-second game round.

The backend was not examined. Payload sizes from /sessions/start, /questions/next and /leaderboard, and their server-side latency, are outside this pass and could easily dominate the client-side numbers above during a busy session. Worth a look at pm-trivia-BE before the event.

PERF-02's claim that Inter never loads is inferred from the build's own invalid-@import warning and the CSS specification. It should be confirmed in thirty seconds by opening the deployed site and checking whether the Network panel shows a fonts.gstatic.com request — do that before treating it as fact.

What is already right

Worth stating plainly, because an audit reads as a list of failures. Every route is lazy (loadComponent), every component is ChangeDetectionStrategy.OnPush with no exceptions, every @for has a track, there is not a single *ngIf or *ngFor left in the templates, state is properly signal-based, and the question-buffering design does exactly what the brief asks. The structure is in good shape — which is why the findings above are concentrated in assets, configuration, and two timer loops rather than in the architecture.
